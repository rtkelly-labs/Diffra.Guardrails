# Interventions

The rules in [VISION.md](../VISION.md) say what a good test looks like. This page is about getting
there by default. A rule that only fires in CI reaches an agent after it has finished and moved on,
which is the most expensive moment to learn anything. Each layer below moves the rule earlier, or
makes the result cheaper to act on, or shows whether it worked.

Status: design proposal, 6 November 2026. Nothing here is built yet.

For each layer: what it does by default, what it costs each repository that adopts it, and how to
tell whether it helps. The roll-out order is at the end.

## Principles

- **One rule text, many surfaces.** The `AGENTS.md` block, the skill, hook output, annotations and
  the job summary all render the same per-rule `message` and `fix` text. Change it once.
- **The DFA rules are syntactic.** Every rule can be checked from one file's syntax tree and its
  comments, with no build and no test run. That is what makes edit-time feedback fast enough to put
  in an agent's loop, including for C#.
- **Measure, then intervene.** Each intervention is switched on only after the measure it should
  move has a baseline. Interventions are added one at a time per repository, so an effect can be
  attributed.
- **Cheap in CI.** The target repositories include private ones with limited Actions minutes. The
  checker runs inside jobs that already exist; it never needs a build of its own.
- **Deterministic.** No language model checks anything. Agents are the main reader, not the judge.

## 1. Authoring defaults

The cheapest finding is the one never raised. An agent copies what is in front of it, so put the
right shape in front of it.

### What it does by default

- **An `AGENTS.md` block per repository**, generated by `diffra-guardrails agents-md` between
  `<!-- diffra-guardrails:begin -->` and `<!-- diffra-guardrails:end -->` comments. It holds, for that
  repository's languages only: the marker form, the size budgets and how to declare a size, the
  message rule, the exemption form, the command that checks a file, and links to two or three
  **exemplar tests already in the repository**. Under 40 lines, because instruction files are read
  every session. `agents-md --check` fails CI when the block is out of date.
- **Exemplars over prose.** The block names real, converted tests (one small Arrange/Act/Assert, one
  shared-context class, one medium When/Then test). An agent imitates a nearby example more
  reliably than it follows a description.
- **A test-writing skill**, in the Agent Skills `SKILL.md` format, shipped from this repository. It is
  a procedure, not rules: find the exemplar, pick the size from what the test will touch, write the
  markers first, one behaviour per test, cases as a data-driven test, run the checker on the file.
  The rules stay in `AGENTS.md`; the skill only says how to work.
- **Editor snippets** for people: VS Code `.code-snippets` and Rider live templates for an
  Arrange/Act/Assert test, a Given/When/Then test and an Act & Assert test in each language.
- **A scaffold command**, `diffra-guardrails new test --size small "a discount is taken off the
  total"`, which writes a marked, empty test into the right file with the right size declaration.
  Useful to agents as a known-good starting shape.

**Cost per repository.** Run `agents-md` once and pick the exemplars (minutes, after the first tests
are converted). Snippets and the skill are installed once per machine. Nothing to maintain beyond
the `--check` step.

**How to measure.** Findings per agent pull request and first-push pass rate (see
[Measurement](#6-measurement)) in the two weeks before and after the block lands, in the same
repository with no other intervention changed.

## 2. Edit-time feedback

Findings delivered while the agent still has the file open are fixed in the same turn.

### What it does by default

- **A Claude Code `PostToolUse` hook** on `Edit|Write|MultiEdit`. The hook reads the edited path
  from the event, exits at once if it is not a recognised test file, and otherwise runs
  `diffra-guardrails hook` on that one file with the merge-base scope. If any **gated** finding
  remains, it prints them in agent format (rule, line, `fix`) to standard error and exits 2, which
  Claude Code passes back to the model. Ungated findings stay silent, so the hook never nags about
  tests the agent did not touch. Any internal error exits 0 with a one-line note: a broken hook must
  never block work.
- **Per-file speed for every language.** Python runs the checker in-process. TypeScript runs
  ESLint on the one file. C# uses a syntax-only mode of the C# adapter, shipped as a small .NET tool
  that parses the single file with `CSharpSyntaxTree.ParseText` and needs no project build. Target:
  under a second per edit.
- **An optional `Stop` hook**, off by default, that refuses to end a turn while changed tests still
  have gated findings. It guards on `stop_hook_active` so it cannot loop. It is a separate
  experiment because it is more intrusive.
- **pre-commit**, for every other agent and for people: a `.pre-commit-config.yaml` entry running
  `diffra-guardrails check --staged`. It is the one edit-time surface that works for any agent.
- **IDE diagnostics for free** in C# and TypeScript: the Roslyn analyzer and ESLint plugin show
  squiggles in Rider, Visual Studio and VS Code, with code fixes for marker spelling. Python gets a
  VS Code problem-matcher task over `check --format github`.

The hook configuration ships as a template for `.claude/settings.json`. It is configuration, not
instructions: the target repositories keep `AGENTS.md` as their only agent-instruction file and add
no `CLAUDE.md`.

**Cost per repository.** One settings template and one pre-commit entry. The tool itself is a .NET
tool, installed once per machine or run without installing through `dnx`.

**How to measure.** The hook appends one line per firing to a local log under `.git/` (path, rules,
whether the next check of that file was clean). From it: findings caught at edit time, and turns
taken to get a file clean. The outcome measure is the first-push pass rate, compared before and
after the hook in the same repository.

## 3. CI

### What it does by default

A composite action, `rtkelly-labs/Diffra.Guardrails/action`, pinned by commit SHA. It is a set of
steps added to jobs a repository already runs, not a job of its own, because a fresh runner and a
toolchain install would cost more minutes than the check.

- **Where it runs.**
  - Python: after the existing test step, so it can read a measured-size file if the test run wrote
    one.
  - C#: after the existing build. The analyzer has already run during the build; the action reads
    the SARIF file written with `-p:ErrorLog=...`.
  - TypeScript: after the existing lint step, reading `eslint --format json` output.
- **Scope.** The checkout uses `fetch-depth: 0` with `filter: blob:none`, so the merge-base resolves
  without downloading old file contents. A test is new when its qualified name is absent at the
  merge-base, and changed when the diff touches its span. An unresolvable merge-base fails with a
  hint; it never passes silently.
- **Annotations.** Each gated finding becomes `::error file=...,line=...,title=DFA105::<message>`.
  GitHub keeps only about ten error annotations per step and drops the rest without saying so, so
  the action writes the first ten and one `::notice` pointing to the job summary for the rest.
- **Job summary.** Gated findings with their fixes; the score change by rule, and the files whose
  counts rose; each exemption added in the pull request with its reason.
- **Diffra payload.** The three payloads from [docs/adapters.md](adapters.md#the-diffra-metrics-payload)
  are uploaded as one artifact on every run. A run on `main` is the trusted baseline for later pull
  requests. `diffra collect --commit` gets the pull request's head SHA, not `github.sha`, which on
  `pull_request` events is a synthetic merge commit.
- **Baseline provenance.** The baseline is the payload artifact from the trusted `main` run at the
  merge-base commit, never a file the pull request supplies. If that artifact has expired, the
  action regenerates the payload at the merge-base in a worktree when that is cheap (Python and
  TypeScript need no build), and otherwise compares against the newest `main` artifact and marks the
  result `needs-review`.
- **Diffra evaluation.** In .NET repositories the SDK is already on the runner, so `diffra diff` and
  `diffra eval` run in place. Elsewhere, a small follow-on job runs them only when the payload's
  digest differs from the baseline's, so most pull requests spend nothing on it.
- **PR comment, optional and off by default.** When enabled, it posts the summary as one sticky
  comment using the `sticky-comment` action from `rtkelly-labs/github-actions`. It needs
  `pull-requests: write` and is skipped on pull requests from forks.
- **Modes.** `mode: report` writes everything and never fails; `mode: gate` fails on gated
  findings. A repository starts in `report`.

Code scanning (SARIF upload) is deliberately not used: on private repositories it requires a paid
GitHub Advanced Security licence, and annotations plus the summary give the same information.

**Where the action lives: here.** The shared `rtkelly-labs/github-actions` repository is
pure Python with zero runtime dependencies, and its README states that it has no Diffra dependency,
with a future Diffra adapter consuming its evidence from outside. A Guardrails action needs
language toolchains and the Diffra CLI, so putting it there would break that repository's contract.
It lives in this repository, versioned with the checkers it calls, and reuses `sticky-comment`
from `github-actions` rather than writing its own comment logic.

**Cost per repository.** One `uses:` step in each job that already builds, tests or lints; a
`permissions: actions: read` line so the baseline artifact can be fetched. Added runtime: seconds
for the checker, plus the occasional evaluation job.

**How to measure.** The action writes a run record (pull request number, head SHA, attempt, agent
or person, gated findings by rule, exemptions added, new tests) as part of its artifact. These feed
every measure in section 6.

## 4. Wrappers

### What it does by default

- **One CLI, `diffra-guardrails`**, written in C# and published to NuGet as a .NET tool, run
  through `dnx` or `dotnet tool`. It dispatches to each language's checker and prints one format:
  - `check [--changed | --staged | --all] [--base <ref>] [--files ...] [--format agent|json|github|summary]`
  - `ingest --sarif <file> --eslint <file>` maps analyzer and ESLint output already produced by a
    build onto the shared finding shape, so CI never runs a checker twice;
  - `payload --out <dir>` writes the three Diffra payloads;
  - `hook claude`, `agents-md [--check]`, `new test`, `codemod markers`, `init`.

  The CLI is C# because this repository's tooling is, and because the C# adapter's syntax-only
  mode can live in the same tool. Each language's checker stays in the language it parses best: the
  Python checker is Python (stdlib `ast` and `tokenize`) and the CLI runs it as a child process, so a
  Python repository needs the .NET SDK only for the CLI, and can run the Python checker on its own
  in the hook and pre-commit, with the same finding format.
- **The marker codemod.** `codemod markers` inserts Arrange/Act/Assert comments only where the shape
  is unambiguous: an optional setup, a single Act statement, then only assertions. Everything else
  is listed, not touched. It only adds comments, and it proves this: in Python the `ast.dump` of
  each file is identical before and after; in C# and TypeScript the token stream minus comments is
  compared. It is run once per repository, as its own pull request, and clears most of DFA101.
- **Runner plugins that improve failure output.** A pytest plugin and a Vitest reporter add one
  line under a failing assertion that has no message: which rule it breaks, and that a message
  saying what behaviour broke would let the reader skip the debugger. They also record each failure
  with whether its assertion had a message. .NET is left out at first: APIs with a message slot
  already print it on failure, and APIs without one get the DFA106 warning instead.

**Cost per repository.** None for the CLI. The codemod is one pull request. The runner plugins are
one dev dependency and one line of configuration.

**How to measure.** For the codemod: DFA101 count before and after, and no change in test results.
For the runner plugins: the share of CI test failures whose assertion had a message, and, where an
agent fixes the failure, the number of turns it took, compared between messaged and unmessaged
failures.

## 5. Baseline and ratchet

### What it does by default

Two template rules files, one per evaluated payload. Diffra applies one threshold set to every
measurement in a Delta, so different budgets need different files.

```json
{
  "id": "diffra.guardrails.test-structure",
  "version": "1.0.0",
  "failAboveAbsoluteIncrease": "0"
}
```

```json
{
  "id": "diffra.guardrails.test-structure-score",
  "version": "1.0.0",
  "warnAboveAbsoluteIncrease": "0"
}
```

- **Absolute budgets only.** A relative threshold against a zero baseline is `needs-review` in
  Diffra, and most per-file counts start at zero.
- **Per file.** Any increase in any rule in any file fails the structure budget, so a fix in one
  file cannot pay for a regression in another.
- **What Diffra adds beyond the gate.** The changed-test gate already stops new violations in the
  tests a change touches. Diffra is the backstop for what that scoping misses (renames, moved files,
  a fixture edited out from under its tests) and the record of the score over time.
- **Exemptions** are counted per rule in the score payload. An increase warns, and the job summary
  lists each new exemption with its reason so a reviewer reads it. File-wide or project-wide
  suppression of a gated rule is rejected outright. Exemptions per agent pull request is tracked in
  section 6, because it is how an agent would game the gate.
- **Known cost of sparse payloads.** A file cleaned to zero shows as `removed`, which Diffra marks
  `needs-review`. Cleaning a file is a good change, so the action reports that case as "cleaned"
  rather than as a problem. Whether a missing measurement can be read as zero is decided per
  measurement: yes for violation counts, no for totals. A per-measurement declaration in Diffra
  would remove the cost.

### Day one, with no friction

1. `diffra-guardrails init` writes the configuration, both rules files and the `AGENTS.md` block.
2. The action goes in with `mode: report`. Nothing can fail.
3. The first push to `main` uploads the first baseline. From then on every pull request is scored
   against the baseline at its merge-base.
4. After the measurement window, switch to `mode: gate`. Only new and changed tests are gated, so
   no existing test has to change for this switch to pass.

**Cost per repository.** `init`, then a one-line change from `report` to `gate`.

**How to measure.** The repository score by rule, by month; and `needs-review` outcomes per pull
request, which should be rare. If they are not, the payload design is wrong.

## 6. Measurement

The question is whether agents' tests get better, not whether the checker finds things. Every
measure has a definition, a denominator and a source, and is collected for at least two weeks
before the intervention it judges is switched on.

**Agent pull requests** are those whose commits carry a `Co-Authored-By:` trailer naming an agent
(Claude Code adds one by default), or that carry an `agent` label. The trailer usually names the
model, which is recorded, because a model change is the largest confounder in any before-and-after
comparison.

| Measure | Definition | Source | Cadence |
| --- | --- | --- | --- |
| Findings per agent PR | Gated findings on the first CI run of an agent PR, by rule, per new or changed test | Run records | Every PR; monthly roll-up |
| First-push pass rate | Share of agent PRs whose first CI run passes the Guardrails gate (in `report` mode: would pass) | Run records | Monthly |
| Edit-time catch | Findings the hook returned, and turns until the file was clean | Local hook log | Sampled |
| Message coverage of new tests | Assertions with a message ÷ assertions, in new tests only | Totals payload | Every PR |
| Exemptions per agent PR | New exemptions, by rule | Score payload | Every PR |
| Mutation score of new tests | Mutants killed per new test, in the modules each PR touched | Stryker.NET, StrykerJS, mutmut on a weekly schedule | Weekly |
| Message usefulness | For a sample of killed mutants whose killing assertion has a message, whether the message alone says what broke | Manual review of 20 a month | Monthly |

- **Mutation score is the outcome.** The other measures show the rules are followed; mutation
  score shows whether following them made tests better at catching faults (Just et al., FSE 2014;
  Petrović et al., ICSE 2021). It runs on a weekly schedule over changed modules only, never per pull
  request, to keep minutes down. It compares tests written under the rules with tests written
  before them in the same modules. If DFA105 makes new tests kill fewer mutants, DFA105 changes.
- **Roll-up.** A monthly scheduled workflow in each repository reads the last month's run records
  through the GitHub API (artifacts expire, so it runs well inside the retention window) and writes
  them as a Diffra metrics payload, so the trend itself is evidence with a baseline.
- **Decision rule.** An intervention stays if its measure moved in the expected direction over two
  windows without the mutation score of new tests falling. Otherwise it is removed and the result
  is written down. A negative result is a result.

## Recommended roll-out

One repository first, then the rest by language. Each step starts only when the previous step's
measure has a baseline.

1. **Measure only.** In the first Python repository, where the checker is already being trialled:
   the action in `report` mode, run records on, and a first weekly mutation sample. Two weeks.
2. **`AGENTS.md` block and exemplars** in that repository. Measure findings per agent PR.
3. **Gate.** Switch that repository's action to `mode: gate`.
4. **Claude Code hook.** Measure first-push pass rate and edit-time catch.
5. **Diffra rules files** and evaluation, once the payload has run on `main` long enough to trust
   the baseline.
6. **Move the Python checker into this repository** behind the C# CLI, and publish both. Adopt it in the
   second Python repository from step 2 onwards.
7. **C# adapter**: the syntax-only tool for the hook first, then the Roslyn analyzer for the IDE and
   CI. It passes the conformance corpus before any .NET repository adopts it. Diffra itself is the
   first .NET adopter.
8. **ESLint plugin** for the TypeScript repositories, starting with the design system's Vitest
   suite.
9. **Codemod** per repository, each as its own pull request.
10. **Runner plugins, then F#.**

Not planned: a language model reviewing tests (not deterministic, and Diffra already reviews the
evidence); a PR comment on by default (noise, and it needs write permissions).
